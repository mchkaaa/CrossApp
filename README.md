# CrossApp
 Наскрізний проєкт з крос-платформного програмування.
 Предметна область: Замовлення. Сутності: Customer, Product, Order, OrderLine.
 Призначення: оформлення замовлень і підрахунок сум.
 ## Запуск
 dotnet build
 
 dotnet run --project src/Cli
 ## Середовище
 .NET SDK 8.0, Windows 11 x64
## Додаткове завдання: Порівняння розмірів self-contained збірок

Було виконано публікацію `self-contained` застосунку під дві різні платформи (RID). 
Результати порівняння розмірів каталогів:

* **win-x64**: 140 МБ (147 833 626 байтів), 374 файли.
* **linux-x64**: 141 МБ (147 868 562 байтів), 374 файли.

Висновок: Розміри self-contained збірок для Windows та Linux практично однакові. Вони займають багато місця (близько 140 МБ), оскільки тягнуть за собою весь необхідний .NET Runtime для автономної роботи.
## Лабораторна робота 2: Архітектура та Публікація

Проєкт розділено на два модулі: `Core` (бібліотека класів із логікою збору даних) та `Cli` (консольний застосунок для форматування та виводу). Додано `ProjectReference` від `Cli` до `Core`.

### Режими публікації та їх порівняння

| RID | Режим | Розмір `publish` | Потрібен runtime |
| :--- | :--- | :--- | :--- |
| `win-x64` | `self-contained` | ~70,5 МБ | ні |
| `win-x64` | `framework-dependent` | ~187 КБ | так (.NET 8.0) |

**Висновок:** 
`self-contained` публікація займає значно більше місця, оскільки містить у собі середовище виконання .NET, необхідне для автономної роботи. `framework-dependent` містить лише скомпільований код застосунку, тому займає дуже мало місця, але вимагає попередньо встановленого .NET SDK/Runtime на цільовій машині.

## Лабораторна робота 4: Багата предметна модель (Domain-Driven Design)

У цій лабораторній роботі реалізовано патерн "Rich Domain Model". Вся бізнес-логіка інкапсульована в сутностях предметної області (шар `Core/Domain`), який є повністю незалежним від введення/виведення, `Console`, `File` чи `Cli`.

**Перелік реалізованих інваріантів (бізнес-правил):**

* **Product (Товар):**
  * Назва товару не може бути порожньою або складатися лише з пробілів.
  * Ціна товару не може бути від'ємною.
  * Кількість товару при надходженні (Receive/RegisterArrival) повинна бути більшою за нуль.
  * Не можна видати (Issue) товару більше, ніж фактично є на залишку.
  * Створення об'єкта відбувається виключно через фабричний метод (конструктор приватний).
* **OrderLine (Рядок замовлення):**
  * Ціна не може бути від'ємною, а кількість повинна бути строго більшою за нуль.
* **Order (Замовлення):**
  * Створення об'єкта відбувається виключно через фабричний метод (конструктор приватний).
  * Зміна статусів (`OrderStatus`) суворо контролюється через `switch expression`. Дозволено логічні переходи (наприклад, `Draft` -> `Confirmed`), але заборонено нелогічні (наприклад, з `Confirmed` назад у `Draft`).
* **OrderService (Доменний сервіс):**
  * *Інваріант для кількох сутностей:* Клієнт не може створити нове замовлення, якщо у нього вже є 3 активні замовлення.

Усі порушення інваріантів генерують відповідні винятки (`ArgumentException`, `ArgumentOutOfRangeException`, `InvalidOperationException`), які безпечно перехоплюються на рівні `Cli`.
