# CrossApp
 Наскрізний проєкт з крос-платформного програмування.
 Предметна область: Замовлення. Сутності: Customer, Product, Order, OrderLine.
 Призначення: оформлення замовлень і підрахунок сум.
 ## Запуск
 dotnet build
 
 dotnet run --project src/Cli
 ## Середовище
 .NET SDK 8.0, Windows 11 x64
## Додаткове завдання: Порівняння розмірів self-contained збірок

Було виконано публікацію `self-contained` застосунку під дві різні платформи (RID). 
Результати порівняння розмірів каталогів:

* **win-x64**: 140 МБ (147 833 626 байтів), 374 файли.
* **linux-x64**: 141 МБ (147 868 562 байтів), 374 файли.

Висновок: Розміри self-contained збірок для Windows та Linux практично однакові. Вони займають багато місця (близько 140 МБ), оскільки тягнуть за собою весь необхідний .NET Runtime для автономної роботи.
## Лабораторна робота 2: Архітектура та Публікація

Проєкт розділено на два модулі: `Core` (бібліотека класів із логікою збору даних) та `Cli` (консольний застосунок для форматування та виводу). Додано `ProjectReference` від `Cli` до `Core`.

### Режими публікації та їх порівняння

| RID | Режим | Розмір `publish` | Потрібен runtime |
| :--- | :--- | :--- | :--- |
| `win-x64` | `self-contained` | ~70,5 МБ | ні |
| `win-x64` | `framework-dependent` | ~187 КБ | так (.NET 8.0) |

**Висновок:** 
`self-contained` публікація займає значно більше місця, оскільки містить у собі середовище виконання .NET, необхідне для автономної роботи. `framework-dependent` містить лише скомпільований код застосунку, тому займає дуже мало місця, але вимагає попередньо встановленого .NET SDK/Runtime на цільовій машині.

## Лабораторна робота 4: Багата предметна модель (Domain-Driven Design)

У цій лабораторній роботі реалізовано патерн "Rich Domain Model". Вся бізнес-логіка інкапсульована в сутностях предметної області (шар `Core/Domain`), який є повністю незалежним від введення/виведення, `Console`, `File` чи `Cli`.

**Перелік реалізованих інваріантів (бізнес-правил):**

* **Product (Товар):**
  * Назва товару не може бути порожньою або складатися лише з пробілів.
  * Ціна товару не може бути від'ємною.
  * Кількість товару при надходженні (Receive/RegisterArrival) повинна бути більшою за нуль.
  * Не можна видати (Issue) товару більше, ніж фактично є на залишку.
  * Створення об'єкта відбувається виключно через фабричний метод (конструктор приватний).
* **OrderLine (Рядок замовлення):**
  * Ціна не може бути від'ємною, а кількість повинна бути строго більшою за нуль.
* **Order (Замовлення):**
  * Створення об'єкта відбувається виключно через фабричний метод (конструктор приватний).
  * Зміна статусів (`OrderStatus`) суворо контролюється через `switch expression`. Дозволено логічні переходи (наприклад, `Draft` -> `Confirmed`), але заборонено нелогічні (наприклад, з `Confirmed` назад у `Draft`).
* **OrderService (Доменний сервіс):**
  * *Інваріант для кількох сутностей:* Клієнт не може створити нове замовлення, якщо у нього вже є 3 активні замовлення.

Усі порушення інваріантів генерують відповідні винятки (`ArgumentException`, `ArgumentOutOfRangeException`, `InvalidOperationException`), які безпечно перехоплюються на рівні `Cli`.

### Лабораторна робота 6: Події, делегати та замикання
- **Система подій:** Додано подію `Changed` (тип `EventHandler<OrderChangedEventArgs>`) у клас `OrderService` для безпечного відстеження життєвого циклу замовлення.

- **Dependency Injection (Додаткове завдання):** Реалізовано альтернативний механізм сповіщень через інтерфейс `INotificationSink` із двома імплементаціями (`ConsoleSink`, `FileSink`).
- **Делегати (Додаткове завдання):** Використано делегат `Action<string>` для гнучкої обробки помилок під час імпорту даних замість використання механізму `throw Exception`.


# Лабораторна робота 7: LINQ та відкладене виконання

## 1. Основне завдання
У ході виконання базової частини лабораторної роботи було реалізовано:
* **DTO-моделі:** Створено рекорди `OrderLine` та `GroupSummary` для проєкції даних без зміни основної доменної моделі.
* **Сервіс звітів (`ReportService`):** Реалізовано методи для аналітики замовлень з використанням методів розширення LINQ (`Where`, `Select`, `GroupBy`, `Sum`, `Average`, `Max`).
* **Тестові дані:** Сховище `InMemoryOrderStore` наповнено 20 заздалегідь згенерованими записами (`SampleData`) із різними сумами та статусами.
* **Відкладене виконання (Deferred Execution):** Продемонстровано, що LINQ-запит не виконується в момент його оголошення. Коли нове замовлення було додано до списку *після* створення запиту, але *до* його матеріалізації (виклику `Count()` чи `ToList()`), воно успішно потрапило у фінальну вибірку.

## 2. Додаткові завдання 
* **Завдання 1 (GroupJoin):** Реалізовано об'єднання двох колекцій (Клієнти × Замовлення) за допомогою оператора `GroupJoin` із проєкцією результату у зведений рекорд `CustomerOrderSummary`. Продемонстровано поведінку, аналогічну `Left Outer Join` (клієнт без замовлень залишився у вибірці з нульовими показниками).
* **Завдання 2 (Власний метод розширення):** Написано метод розширення `TopBy<T>`, який інкапсулює логіку `OrderByDescending().Take()`. Метод успішно застосовано у двох різних звітах.
* **Завдання 3 (Синтаксис запитів):** Звіт групування замовлень за статусами переписано з використанням синтаксису запитів (`from ... group ... into`). 
* **Завдання 4 (Stopwatch та ToList):** Проведено тестування продуктивності запитів на колекції зі 100 000 згенерованих записів.

## 3. Аналіз та висновки
### Порівняння синтаксису (до завдання 3)
Синтаксис запитів (Query Syntax) візуально наближений до SQL, що робить його зручнішим для складних операцій об'єднання (`Join`, `GroupJoin`) або створення проміжних змінних через `let`. Однак для послідовних лінійних ланцюжків (фільтрація + сортування + проєкція) методний синтаксис (через крапку) є компактнішим, інтуїтивно зрозумілішим і краще читається зліва направо.

### Продуктивність та вплив проміжних ToList() (до завдання 4)
Тестування через `Stopwatch` на великому масиві даних підтвердило, що виклик `ToList()` посеред ланцюжка LINQ є антипатерном. Він перериває відкладене виконання, змушуючи програму негайно матеріалізувати проміжну колекцію, виділяти під неї нову пам'ять і робити додатковий прохід по даних. Ланцюжок без проміжного `ToList()` працює значно швидше, оскільки елементи обробляються по одному і передаються безпосередньо у фінальний агрегатор `Sum()`.
